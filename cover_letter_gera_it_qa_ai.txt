Окремо тримаю «LLM wiki» по підходу Karpathy (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) — структуровані markdown-нотатки по проєкту (архітектура, конвенції, відомі болі, decisions, словник доменних термінів), які підгружаю в контекст агенту на старті сесії. Це той самий принцип, що описує Karpathy: щоб LLM не «втрачав контекст» між сесіями й не вигадував файлові шляхи / API, які не існують. На практиці — різко падає кількість галюцинацій і помилок у згенерованих тест-кейсах та locator-ах.

Що з цього виходить на практиці (а не у відео-демо):

- Тестова документація (чек-листи, тест-кейси з негативними / boundary / equivalence partitioning сценаріями, баг-репорти, тест-плани) — генерую draft з вимог / Figma / OpenAPI-специфікації, потім сам рев'юю на ризики й покриття. Це не «AI пише за мене» — це AI знімає рутину з 80% boilerplate.

- Аналіз логів. Stack trace / network HAR / серверний лог → AI дає гіпотези root cause з посиланням на конкретні рядки; я верифікую через SQL / повторне відтворення / DevTools.

- CI. GitHub Actions, Docker-обгортки для ранерів, шардинг паралелізації — генерую конфіги через агента, далі сам тримаю responsibility за стабільність пайплайну.

Принцип, який тримаю чітко: AI відповідає за «як» і «скільки», QA відповідає за «що» і які ризики пріоритетні. Кожен AI-вихід йде через моє рев'ю — інакше це не QA, а cargo cult.

ПОЛЕ 1: «Як ви використовуєте AI у роботі?»
===========================================

AI у мене — щоденний робочий інструмент, не експеримент. Основний стек — Claude Code CLI (термінальний агент від Anthropic) + Cursor AI; Codex / Windsurf пробував, Antigravity готовий підняти.

Як використовую щодня:

1) UI-автоматизація (Playwright/Selenium) через Claude Code CLI — основний use-case:
- генерую Page Objects з live-сторінки / DOM зі стабільними локаторами (data-testid > role > text > css), з типізацією;
- скафолджу spec-файли з тест-кейсів у Gherkin / табличному вигляді — далі сам доводжу до production quality (асерти, data-driven, тайм-аути);
- рефактор і дедуплікація хелперів одразу по всій кодовій базі (агент бачить увесь репозиторій);
- розбір flaky-тестів по trace/video/логах — локалізація race conditions, фікс auto-wait / network idle / retry-політик;
- CI-конфіги (GitHub Actions, Docker-обгортки ранерів, шардинг паралелізації).

2) Тестова документація й test design:
- генерація чек-лістів і тест-кейсів із вимог / Figma / OpenAPI (негативні кейси, boundary values, equivalence partitioning);
- рев'ю баг-репортів — другий погляд на severity, reproduction steps, missing info;
- TestRail/Jira-формат за 1 prompt.

3) Аналіз логів і дефектів:
- stack trace / network HAR / серверний лог → гіпотези root cause з посиланням на конкретні рядки;
- SQL-діагностика під схему («знайди всі замовлення з неконсистентним статусом»).

4) API-тестування:
- Postman-колекції з OpenAPI, негативні сценарії, контрактні перевірки;
- mock-дані, payload'и, JWT для фікстур.

Контекст-менеджмент — за «LLM wiki» підходом Karpathy (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). Тримаю структуровані markdown-нотатки по проєкту (архітектура, конвенції, decisions, словник доменних термінів, відомі болі), які підгружаю агенту на старті сесії. Це різко знижує галюцинації — агент не вигадує файлові шляхи й API, яких немає.

Принцип, який тримаю чітко: AI відповідає за «як» і «скільки», QA відповідає за «що» і які ризики пріоритетні. Кожен AI-вихід йде через моє рев'ю — інакше це не QA, а cargo cult. Цей флоу обкатаний end-to-end на пет-проєктах (electro-motors.com, bestprice.com.ua, iGaming-демо) — можу показати живі артефакти, а не «теорію».
